⚠ One deploy step is required

Purchase order numbering writes to a new counters collection. Until the rules are pushed, orders still save correctly — they just come out without a PO-… number and fall back to the document id.

  1. Review the new counters block in firestore.rules
  2. firebase deploy --only firestore:rules
  3. Create one test order and confirm a number like PO-KL-2608-0001 appears on the card
  4. Set a short code on each branch (Settings → General) — it becomes the tag in the number; without one the branch name is used

To switch the approval step on

Settings → Operations & Staff → Purchasing Controls → “Require approval before sending a purchase order”. Off by default, so nothing changes until you flip it. Only owner and branch admin can change the policy itself.

09

Keeping branches out of each other's way

Done

Orders, guides, bills and payments were already per-branch, but three things leaked across them: every branch saw every product, one branch's invoice rewrote the price other branches saw, and two branches would hand the same vendor an identically numbered PO.

  • ✓Products are branch-scoped. branchIds on each item; empty means every branch, which is exactly what pre-existing items look like, so nothing changed for them
  • ✓Items page has three views — This branch, All company items, Retired. Rows not stocked here are dimmed and labelled
  • ✓Pull a product another branch already set up with one click, or stop stocking it here without touching other branches. Uses arrayUnion / arrayRemove, so two branches acting at once cannot overwrite each other
  • ✓Add and Edit carry a “Stocked at” branch picker; Excel import follows whichever view you are in, and says which in the confirm
  • ✓Last-paid price is now per branch — lastPurchaseByBranch.{branchId}, written on a dotted field path so branches never clobber each other. Guides and orders prefer this branch's figure, falling back to the company-wide one for a branch that has never bought the item
  • ✓The item row says whether a price is “last paid here” or borrowed from another branch
  • ✓PO numbers carry a branch tag — PO-KL-2608-0001, taken from the branch code, then its name, then the id. Two branches can no longer issue the same number to one vendor
  • ✓Ordering screens only ever offer what the branch stocks; the full company catalog stays reachable from the Items page alone

Known by design

Vendor balances are company-wide totals

vendor.currentBalance, totalBilled and totalPaid sum every branch — that is deliberate, and SyncVendorMetrics.jsx rebuilds them that way on purpose. Per-branch bill lists on Due Bills and Payments are correctly scoped; it is only the vendor's headline balance that spans the company. Concurrent writes are safe (increment() is atomic server-side), so this is an aggregation choice, not a race. Say the word if a per-branch vendor balance is wanted.

Notes

Every change is additive

No field was renamed or removed and no migration is needed. New fields — poNo, billId, sourcePoId, invoiceAttachment, approvedBy, selfApproved, rejectionReason, branchIds, lastPurchaseByBranch, lastPurchasePrice, isActive, guideItems, lastEditedBy — are all read with fallbacks, so documents written before today behave exactly as they did. An item with no branchIds is treated as stocked everywhere, which is what every existing item looks like. The one behaviour change that is not opt-in is the mandatory invoice attachment, which was asked for explicitly.
